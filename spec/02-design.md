## 1. Overview

A static site generated by **Jekyll** with the **minima** theme, hosted on **GitHub
Pages** at `awadhesh246.github.io`. I write Markdown; GitHub Pages rebuilds and serves
HTML automatically on every push to `main`. No server, no database, no cost.

## 2. Architecture

```
Markdown files (pages + _posts/*.md)
        │   git push to main
        ▼
GitHub Pages (builds Jekyll automatically)
        ▼
Static HTML served at https://awadhesh246.github.io
```

## 3. Key components

| Component | Responsibility |
|-----------|----------------|
| `_config.yml` | Site config: title, theme, social links, nav, excludes. |
| `index.md` | Homepage (`layout: home`) — intro + links + auto post list. |
| `about.md` | About page (`layout: page`). |
| `_posts/*.md` | Blog posts (`layout: post`), named `YYYY-MM-DD-title.md`. |
| `assets/` | Résumé PDF, images. |
| `docs/` | Maintenance guide + post template (excluded from the built site). |
| `spec/` | These SDD artifacts (excluded from the built site). |

## 4. Design decisions (with the reversals kept)

| # | Decision | Rationale | Req |
|---|----------|-----------|-----|
| D1 | **Jekyll + minima on GitHub Pages** | Native to Pages, zero build config, free, low maintenance. | R1, R8, N1–N3 |
| D2 | **Repo named `awadhesh246.github.io`** | GitHub serves user sites from this exact repo name at the root domain. | R1 |
| D3 | **Blog = Markdown files in `_posts/`** | Add a file + push; list is automatic. Lowest-friction publishing. | R4, R8 |
| D4 | **Résumé as a committed PDF in `assets/`; phone kept off web pages** | Easy download; limit public exposure of personal details. | R5, N4 |
| D5 | **Contact = LinkedIn link** | *Reversed decision.* First planned a **Formspree contact form**, then a **WordPress contact page**; switched to LinkedIn because I don't check email frequently — a channel I won't maintain is worse than none. | R7, N3 |
| D6 | **Remove all WordPress references** | Clean start; the GitHub Pages site is the single writing home. | R3 (non-goal migration) |
| D7 | **Per-repo git identity `awadhesh246@gmail.com`; unsigned push** | Keep personal project separate from the work (Ericsson) git identity; GitHub rejects signed pushes. | — |
| D8 | **`docs/` and `spec/` excluded from the build** | Keep guidance/specs in the repo without publishing them as pages. | N3 |

### Reversal note (D5) — why it's recorded
The contact mechanism changed twice: **Formspree form → WordPress contact page →
LinkedIn**. Capturing this is the whole point of living artifacts — the *why* behind
the final choice ("I won't reliably check an inbox") is preserved, so future-me
doesn't re-litigate it or accidentally re-add a form.

## 5. Data / model

- **Page** = a root-level `.md` with `layout: home|page` and front matter.
- **Post** = `_posts/YYYY-MM-DD-title.md` with `layout: post`, `title`, `date`, and
  optional `categories`/`excerpt`. Date+slug set the URL.

## 6. Behavior details

- Homepage uses `layout: home`, which auto-lists posts newest-first.
- Top nav shows pages listed in `header_pages` (currently About).
- Permalink pattern: `/:year/:month/:day/:title/`.

## 7. Error handling / failure modes

- Broken `_config.yml` (YAML indentation) or bad front matter → Pages build fails;
  visible in repo **Settings → Pages** / **Actions**. Fix and re-push.
- Missing asset path → broken link; asset must be committed under `assets/` and
  referenced as `/assets/...`.

## 8. Alternatives considered

| Alternative | Why not |
|-------------|---------|
| **Hugo** | Faster, but needs a GitHub Actions build pipeline — more setup than needed now. |
| **Keep WordPress** | Costs/maintenance and not fully owned; wanted a clean, free, Git-based start. |
| **Formspree contact form** | Works, but adds a third party and an inbox to monitor (D5). |
| **`mailto:` link** | Exposes email publicly (spam) and needs a configured mail client. |

## 9. Risks / trade-offs

- Static site → no dynamic features (comments, forms) without a third-party service.
- Tied to GitHub Pages' approved-plugin list; advanced plugins would need a custom
  Actions build (documented in `docs/MAINTAINING.md` §6).
